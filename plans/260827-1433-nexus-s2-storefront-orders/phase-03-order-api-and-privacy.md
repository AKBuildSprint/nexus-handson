# Phase 3: Order API and Privacy

## Overview

Expose the Order command and reduced read projections through the existing Nexus Worker. Add constrained CORS for the independent Storefront without widening CORS or authorization semantics of Console APIs.

## Requirements

- Storefront obtains public catalog, creates an Order, and opens its private Order route through explicit Worker endpoints.
- The raw opaque capability is generated by Storefront, sent only through `X-Nexus-Order-Capability`, and stored only as a digest. The create response returns safe Order identity data; the Storefront constructs its private URL with the raw capability in the URL fragment, which the network never transmits.
- Private read requires the capability as well as the Store-scoped Order identity. Reference/email alone, altered token, and cross-Store lookup fail without leaking whether an Order exists.
- Customer response shows only reference, purchase-time Product/Variant selection, quantity, amount, currency, `pending_payment`, and static payment next-step.
- Console Orders route returns the approved read-only demo projection: Customer, pending Order, line, quantity, amounts, and Variant selection; no delivery/access/capability data.
- CORS accepts only the configured Storefront origin and only finalized Storefront methods/headers. Success, validation failure, unexpected failure, and preflight follow one controlled policy.

## Architecture

Add separate Storefront-Order and Console-Order route modules, then register them in the single `src/worker/index.ts` dispatcher. Keep catalog `GET /api/storefront/products` canonical and extend its Storefront CORS wrapper rather than adding a catalog replica.

Centralize Storefront CORS policy in a small Worker helper that validates `Origin` against configured environment data. It constructs explicit response headers for the allowed contract and handles `OPTIONS`; it never reflects arbitrary origins and never adds permissive CORS headers to Console routes. The finalized allow-list includes only Storefront request methods and `Idempotency-Key`/`X-Nexus-Order-Capability`. Extend JSON response/error plumbing or wrap route responses so allowed Storefront errors remain readable cross-origin without changing error-envelope shape.

The private Storefront page reads its capability from `location.hash` and sends it only through `X-Nexus-Order-Capability`; the static Storefront request and Worker API request URLs must never contain the raw value.

## Implementation Steps

1. Finalize only the minimum request contract needed by the Storefront: catalog fetch, Order create with `Idempotency-Key` plus `X-Nexus-Order-Capability`, private Order read with `X-Nexus-Order-Capability`, and allowed `OPTIONS`. Keep price/currency/amount out of client authority and capability values out of URLs.
2. Add a configured Storefront-origin binding to the API Worker configuration and generated Worker types. Local tests supply a known test origin; deployment receives the actual provisioned Storefront origin from Phase 1.
3. Implement Storefront CORS policy and apply it to catalog, create, private read, preflight, and their error responses. Allow only the finalized methods and the two required request headers; deny missing/unconfigured origins without reflecting or broadening headers.
4. Implement Storefront routes over the Orders command/read services. Map expected validation, stale catalog, capability, and idempotency outcomes to the established JSON error envelope; never include raw capability/token or internal snapshot in an error.
5. Implement the minimal Console Orders read route over its reduced Orders projection. Keep S1 anonymous-demo behavior; do not add sessions, roles, payments, delivery, or customer capability management.
6. Register all new routes before `routeNotFound()` and preserve Worker-first JSON behavior for `/api` paths and asset fallback for non-API paths.
7. Add integration tests for response allow-lists, CORS allow/deny/preflight, private-read denial cases, server-money authority, idempotency including a lost-response retry using the caller-held capability, safe Console projection, and unchanged public catalog privacy.

## Success Criteria

- [ ] Only the configured Storefront origin can read the Storefront API cross-origin; unrelated origins never receive permissive CORS.
- [ ] Private Order read requires a valid capability supplied in the allowed header and returns only the approved Customer projection.
- [ ] Static/Worker request URLs, logs, and error bodies never contain the raw capability; private URL capability remains fragment-only.
- [ ] Console API displays the approved demo fields without private delivery/capability data.
- [ ] All Order route errors keep the established JSON envelope and never log or echo a raw capability.

## Risk Assessment

- Adding CORS solely to success responses makes validation failures unreadable to the real Storefront and encourages unsafe client fallbacks. Apply one policy around every Storefront response path.
- Adding CORS globally would unnecessarily expose Console APIs; limit the policy to Storefront contract routes.

## Security Considerations

- Do not use `Origin` reflection, wildcard origin, wildcard headers, or credentialed CORS.
- Normalize error messages for failed private reads so they do not reveal reference validity, Store membership, or token state. Redact both idempotency and capability headers from application diagnostics.
