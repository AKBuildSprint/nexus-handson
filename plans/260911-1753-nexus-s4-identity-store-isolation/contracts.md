## Scope and decision provenance

- **Outcome:** share the existing Store A with real Owner/Staff identities, assigned work and final Owner Refund decisions; prove Store B isolation and public/Customer continuity.
- **Constraints:** preserve `store_nexus`, records, IDs, capability digests, payment evidence, historical actors, snapshots and retained R2 references; append migrations; packages own domain SQL; existing tokens/navigation remain.
- **Confirmed by user in source brainstorm:** Staff assigned-only reads and writes; Staff read-only Products; one Refund Request per Order across terminal decisions.
- **Engineering choices:** one D1, explicit Store scope, narrowly owned identity package, Better Auth email/password with public signup disabled. The adapter/version is subject to Phase 1 runtime proof, never a claimed existing dependency.
- **Membership decision confirmed by user, 2026-09-12:** use separate login accounts per Store in S4, no Store picker. Each account has at most one active membership; private access requires exactly one. Keep unique `(user_id, store_id)` and retained revoked membership history; no lifetime uniqueness or account-transfer feature is added. Provisioning never silently repurposes a login for another Store.
- **Non-goals:** signup/invitations/team administration, Store-picker UI, new delete APIs, new navigation, framework rewrite, S5 execution/money movement, S6 MCP.
- **Complexity:** eight phases preserve distinct runtime, schema, auth, catalog, Orders, Refund, UI and populated-rehearsal gates. Source ownership crosses phases; execute sequentially by default. Do not run overlapping edits concurrently merely because dependencies permit it.

## Proposed HTTP and client contract

Existing `/api/console/orders/:reference` routes keep their paths and `X-Nexus-Order-Contract: 2`. Extend the version-2 response with assignment and terminal Refund fields; update every active consumer and test together. Historical contract-1 ledger rows retain their existing refusal rules. New endpoints below are proposed, not present in the checkout.

| Endpoint | Authority and response |
|---|---|
| `POST /api/auth/sign-in/email`, `POST /api/auth/sign-out` | Explicit native endpoint allowlist; retain library CSRF/rate limits/cookies, project sign-in success to `{ok:true}`; all other auth endpoints unavailable |
| `GET /api/console/session` | Current session + exactly one active membership; `{user:{id,name},store:{id,name},role,allowedActions}`; no session token/account fields |
| `GET /api/console/staff` | Owner only; `{staff:[{userId,name}]}` for active same-Store Staff, no credentials/email required |
| `POST /api/console/orders/:reference/assignment` | Owner only; strict `{assigneeUserId}` + existing `Idempotency-Key` and Order contract header; returns the shared command-result envelope with `action:'assign'` and recorded assignment projection below |
| `POST /api/console/orders/:reference/refund-requests/:requestId/approve` | Owner only; strict empty JSON object + command key/header; returns existing command-result envelope with terminal Refund projection |
| `POST /api/console/orders/:reference/refund-requests/:requestId/reject` | Same as Approve; separate action/hash; no new decision-reason product requirement |

Assignment replays return the recorded assignment event, not a new reassignment; UI refetches current assignment afterward. A fresh key targeting the already-current assignee binds the current assignment event as a no-op after live Owner/target membership checks; no duplicate assignment event or changed timestamp. New commands hash Store-scoped target, actor identity, action and normalized body. Reuse the existing Store/key uniqueness; another actor/intent using the key conflicts. All path identities are decoded safely; malformed/foreign target uses concealed 404. Do not accept body role/Store/actor/terminal-state authority.

Assignment uses the existing `OrderCommandResult`/ledger/recovery pipeline, not an endpoint-only ledger. Add an action-discriminated assignment branch: `{reference,action:'assign',status,occurredAt,paymentId:null,refundRequest:null,assignment:{assigneeUserId,eventId}}`. `status` is the unchanged Order status recorded by that event, and `occurredAt` is its immutable time, not the current Order/assignment state. Other command responses keep their existing shape without `assignment`; Customer projections never receive it. Migration0009 adds nullable `order_history.assignee_user_id` with same-Store membership FK; history action `assigned` requires that target and real actor with equal before/after Order status, while legacy/non-assignment branches leave the target null. Command CHECK admits contract2 `assign`, using existing `result_history_id` to reconstruct the projection; no extra result table/columns. Current `order_assignments.history_id` references that same event with Order/Store composite FK. Enforce action/event compatibility when reading/binding the result. Types, shared result reader, HTTP adapter and Console parser change together; migration0010 retains these fields/branches.

Console errors keep `ErrorEnvelope` from `apps/worker/src/http-response.ts`. Order of checks: session (401 `unauthenticated`), live membership (403 `store_access_denied`), same-origin mutation proof (403 `origin_not_allowed`), concealed resource lookup (404 `not_found`), permission (403 `forbidden`), contract/body/state/key validation (existing 400/409 codes). D1/session lookup outage yields safe 503 `service_unavailable`, not 401/logout or anonymous access. Collection requests have no target lookup. Endpoint-specific parsers may validate syntax needed to locate a resource, never disclose its content before authorization. Unknown routes remain route-not-found. Use raw test requests without implicit `X-Nexus-Order-Contract` injection to prove missing/stale/malformed/valid header precedence across anonymous, revoked, foreign and authorized callers.

All Console success/error responses use `Cache-Control: no-store`. Session bootstrap is Console-only, not a Customer projection. Worker resolves sessions with server-side `auth.api.getSession`; native `/api/auth/get-session`, account/user/password management and signup routes are not mounted. Sign-in response adapter preserves status and every `Set-Cookie` while omitting the library body token/user/session metadata; return `{ok:true}` on success and then fetch Console bootstrap. Keep bounded library error semantics and Retry-After; test redaction and multiple-cookie preservation. Sign-out preserves cookie-expiry headers. Resource `allowedActions` intersects the central role policy with current assignment and domain transition rules; coarse session actions cannot grant a resource operation. All GET detail/count/history/payment queries must apply current membership/visibility in SQL, including after async work.

Audit correction (2026-09-12, session headers): keep library session refresh enabled. Internal `getSession` resolution must return its response headers as well as session data; the Worker appends every library `Set-Cookie` separately to the final Console response, including bootstrap and early 401/403/404/error responses after resolution. Keep this request-scoped header accumulator outside the domain `IdentityContext`; never expose it in JSON or attach it to public/Customer responses. Do not comma-join cookies or overwrite another cookie. Preserve refresh/expiry attributes, sanitized bodies and no-store. Expired/missing persisted sessions may carry library deletion cookies; an infrastructure outage must not synthesize logout cookies. Phase 3 proves due-refresh, expired-cookie cleanup and error-path forwarding; Phase 7 verifies the browser receives refreshed expiry without losing private state.

## Origins, sessions and account provisioning

Local supported Console origin is `http://127.0.0.1:5173`; isolated Worker tests explicitly inject `CONSOLE_ORIGIN=https://local.invalid` with matching request URL and browser Origin; Storefront is separately configured. Test that request URL does not implicitly become a trusted Origin by using a different configured origin and sending the request-host origin as a negative case. Run a separate matching loopback-origin configuration in E2E. Never add test origins to deployment trust. A localhost variant works only when the full configured origin and test server agree. HTTPS deployment uses the exact returned Console origin, host-only HttpOnly session cookies, Secure on HTTPS and SameSite=Lax; disable cookie-session caching and cross-subdomain cookies.

For Nexus cookie-authenticated mutations require an exact configured `Origin`; reject absent, `null`, malformed and foreign origins. If `Sec-Fetch-Site` is present it must be `same-origin`. Only `Sec-Fetch-Site` may be absent for supported test clients; those clients must still send the exact `Origin`. Absence of both headers is rejected. CORS is not a substitute for this rule. Better Auth endpoints retain the pinned library's own CSRF/origin policy and tests; do not invent a wrapper that bypasses library checks. Storefront is never an auth trusted origin. Existing public/capability CORS remains distinct.

Auth configuration memoization may retain only immutable binding/config state, never a user, session, membership or actor. Key reuse must account for DB, secret and origin changes (or instantiate per request if negligible). No account implicitly gains membership on successful sign-in. Disabled signup must also block direct endpoint calls.

Provisioning must use the pinned library password format and credential provider semantics. User/account writes are not guaranteed to form an interactive D1 transaction: require repeat/conflict/partial-failure recovery and membership only after credential success. Exact existing identities are no-op; conflicts never reset passwords or repurpose Store/role. A script cannot pretend a remote D1 HTTP handle is a local `D1Database`; Phase 8 defines the operator transport and proof before remote execution.

## Authorization and atomic writes

The pure identity evaluator owns the action/role matrix. Persistence translates those requirements into predicates over current membership and assignment; parity tests cover Owner, assigned/unassigned Staff and revocation. No module-level user state. Public Storefront uses an explicit Store A route context; Customer operations require their exact capability and cannot inherit Console authority.

D1 `batch` is the transaction boundary, not a read/check followed by independent writes. Capture one command ID/event ID/time. Every business effect is conditioned on current Store membership and the expected resource prestate. The final guard must perform an unconditional INSERT whose non-null ID is a `CASE` over the expected **poststate** and this command's newly inserted event; a zero-row `INSERT ... SELECT` cannot force rollback. A failed guard aborts the whole batch. Never interpret batch success or a different command's existing target state as proof that this command wrote its effect.

Cover `prepareCommand`, `readLedger`, `readCommandResult`, `bindExistingResult`, `recoverFailedBatch`, `runCommandBatch`, and `onConflictReplay`: current authorization precedes result disclosure in initial replay, successful post-batch reads and every recovery callback. If access is lost after a valid commit, retain that commit and return a denial to the later read; do not undo history. A write may succeed only if it commits before revocation/reassignment. Already delivered content cannot be retroactively erased.

Audit correction (2026-09-12, CSV compensation): the uncertain-commit retention rule applies to both delivery uploads and CSV originals. Capture one import ID and exact new R2 key before its D1 attempt. On a batch error, delete only after confirmed rollback or definitive absence of the exact `(storeId, importId, privateObjectKey)` association with no outstanding commit. A server-internal Store-scoped read may establish storage ownership even after membership revocation; a caller-visible denial/filtered lookup is not evidence of absence. If committed or unknown (including lookup failure), retain the original and return a sanitized incident without automatic import resubmission or private-key disclosure. Do not change committed rows, delete retained objects, or add a public import lookup endpoint. Real D1 commit-then-response-error, confirmed rollback/absence, lookup outage and compensation failure tests belong to Phase 4.

Refund decision sequence:

1. Conditional decision-event insert joins matching Store/Order/request in `pending`, current Owner and paid/fulfilled Order. Unique terminal-event constraint spans approve **and** reject for that request.
2. Update that request `pending -> approved|rejected` only when this newly generated event exists. Persist one real `decided_by_user_id` and one `decided_at`; preserve the requester fields. The unique history event links back through `refund_request_id`; no additional cyclic Refund-to-history FK is required.
3. Insert command ledger with non-null guard requiring terminal **poststate**, this event, same actor/time and unchanged Order status/payment evidence. Do not require `pending` after step 2.
4. Same key/action/body/actor replays after current authorization. A new decision key against a terminal request gets 409 state conflict even for the same decision. Opposite decision never binds to the winner.

Submission is different: Customer/Console may submit with a fresh key after a request already exists and receive that original request, including its current terminal status, following existing result-binding behavior. Never replace its reason/requester/time, create another request event, or reopen it. A changed body under the same existing key remains an idempotency conflict. Customer-safe output excludes assignment, actor, internal history/notes and Console payment evidence.

## Delivery and rollout boundaries

Phases 1–7 are local implementation gates, not independently deployable security releases. In particular Phase 3 routing signatures alone do not establish catalog Store isolation; Phase 4 and full acceptance must pass before deployment. Public serving continues except during an explicitly rehearsed writer barrier. Checkpoint is taken **after** all D1/R2 mutation entrypoints are quiescent and drained; a live export alone is insufficient. Keep the barrier active through migration/provisioning/deploy/smoke. Never reopen an anonymous/incompatible writer as rollback.

Current S1/S2 unfinished metadata represents historical verification work; S3 reconciliation and capability layout are completed in plan files and present in source. No unfinished output is needed to draft S4. S4's auth cutover supersedes anonymous Console expectations for future reruns; it does not retroactively mark S1/S2 acceptance complete.
